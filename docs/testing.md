# 测试规范

本页说明 OMP 的测试应当证明什么，以及人工或 Agent 怎样审查这些证据。
运行命令与 CI 范围以[贡献指南](../CONTRIBUTING.md#checks)为准；宿主支持范围以
[Pi 兼容性](pi-compatibility.md#tested-scope)为准。本页不改变检查门禁、发布权限或宿主基线。

## 调研结论

调研截至 **2026-11-19**。通用软件测试、Agent 辅助开发、随机模型行为评测是三件不同的事。
以下来源提供工程依据，不是同一套强制标准；后面的编号条款才是 OMP 的审查口径。

| 依据 | 对 OMP 的启示 |
| --- | --- |
| [Google《Software Engineering at Google》测试概览](https://abseil.io/resources/swe-book/html/ch11.html)及[单元测试](https://abseil.io/resources/swe-book/html/ch12.html)（2020）；[覆盖率实践](https://testing.googleblog.com/2020/08/code-coverage-best-practices.html)（2020-08） | 选能验证契约的最小测试层，覆盖重要行为而不是私有实现；覆盖率用来找缺口，不能替代断言质量。OMP 不设通用覆盖率配额或固定测试层比例。 |

| [NIST SSDF 发布目录](https://csrc.nist.gov/Projects/ssdf/publications)：1.1 正式版（2022-02）、1.2 公开草案（2025-12） | 安全开发指导要求关注可执行代码是否满足安全要求。OMP 将权限、数据外发、制品与发布门禁等失败路径列为优先审查对象；不据此宣称 SSDF 合规，也不把草案当正式要求。 |
| [Meta 的 JiTTesting 工程报告](https://engineering.fb.com/2026/10/29/security/catching-bugs-before-they-land-jittestings-human-on-the-loop-approach-at-full-scale/)（2026-10）与 [FSE 行业论文](https://conf.researchr.org/details/fse-2026/fse-2026-industry-papers/1/Just-in-Time-Catching-Test-Generation-at-Meta)（2026-07）；[OpenAI 对编程评测的独立审查](https://openai.com/index/separating-signal-from-noise-coding-evaluations/)（2026-07） | 实际流程会区分有价值的失败、误报、断言过严和断言漏检。借鉴其做法：先定义期望行为，再独立查证测试能否识别错误；不把企业案例或 benchmark 的数字当作 OMP 的目标。 |

## OMP 审查规则

### T1：断言来自产品契约

- 从需求、公开 API/配置、协议、已确认缺陷或经验证的上游行为取期望值。不能用被测实现的输出当期望，也不要在测试里重写同一算法来求期望。
- 优先断言调用者可观察的结果或状态。工具/通知确实发出、文件确实写入、流正确结束、无权操作没有副作用，比单独断言内部 helper 被调用更有证明力。若调用次数、顺序、精确字节或格式本身就是契约，直接断言相应约束；不要锁定无关细节或无契约顺序。
- 用可读的输入、动作、预期和失败信息说明场景。快照或 fixture 的变更必须能指出哪项契约变了；不能用批量更新预期来消除差异。

### T2：按风险选择最小充分的测试层

| 要证明什么 | 在哪里验证 |
| --- | --- |
| 单包行为，如 schema、协议解析、预算和重试分类 | 实现所有者的 `pi-extensions/<package>/tests/`；不从另一个能力的内部实现借 fixture 或断言。 |
| 包间组合、Pi loader/lifecycle、跨能力取消和隔离 | 所有者内的 Pi loader 测试或 `tests/codex/` 的跨包组合。至少覆盖真实交界，而非把交界的两端一起 mock 掉。 |
| 隔离安装、打包资产、入口和可选依赖 | 交给 `pack:check` 与隔离 tarball 消费者；源码导入成功不能替代安装后的真实入口检查。 |
| CI 规划、发布拒绝条件、不可变制品身份 | `scripts/` 下对应基础设施测试；用本地 fixture 验证，不为此执行真实发布。 |

新行为保留主要成功路径，并针对适用的边界、无效输入、取消和失败补证据。权限、持久化、并发、跨传输重放以及发布门禁等高风险契约，还要验证非法路径确实被拒绝或不产生副作用。纯组合/兼容入口不重复实现所有者测试。覆盖率、表驱动、固定种子的属性测试、针对单个风险的本地反例都可辅助发现缺口，不是每个改动的必选项。

### T3：回归测试要能识别错误

- 修复可复现缺陷时，优先在同一依赖/宿主基线上，用同一个测试观察修复前因**目标断言**失败、修复后通过，并让相邻已支持行为继续通过。编译失败、缺依赖、无关的网络超时或测试没被收集不算复现。
- 无法执行有缺陷的基线时，说明限制；可在隔离副本里用无副作用的小反例证明断言能区分正确和错误行为。不要为了走形式回退共享工作树或引入变异测试框架。
- 不得为消除红灯而跳过用例、放宽断言、改 fixture、伪造状态或降级必需检查。若需求确实删除或修改了契约，解释旧断言为何失效、替代断言证明什么。

### T4：让测试独立、可重复、默认离线

- 控制时钟、随机输入、调度和 I/O；优先用明确的事件、屏障或可控时钟推进，不靠固定睡眠或重跑到通过。并发结果只按契约承诺的顺序检查；对运行本身使用有界超时，避免挂死。
- fixture 使用独立 agent 目录和临时路径，loopback 用临时端口。用清理钩子恢复 `process.env`、`fetch`、stdout、计时器和全局状态，关闭 socket、子进程与监听器，失败路径也执行；同进程内不要并发改共享全局。
- 行为测试用假凭据与明确的 fixture/本地服务，对意外外部请求失败；涉及 SDK 或 tarball 边界时优先跑真实本地交界。默认检查不访问真实模型/通知端点、不读取用户凭据、不产生真实写入；依赖准备和 CI 的准入检查是另有定义的步骤。隔离消费者必须使用根锁投影，不用联网换包或外部链接修复失败。
- 遇到不稳定测试，保留本次失败、输出、环境和可用的种子；用定向复跑诊断测试污染、时序或真实竞态。后来通过不抹消原失败。

### T5：Agent 可以写测试，不能自己定义正确性并自证通过

- 实现/测试作者先记录被测契约、期望/禁止效果和验证路径，再提交代码及实际运行证据。普通改动不要求把编写代码和测试拆成两人；高风险边界及批量修复由未参与该项改动的审查者独立判断行为与断言，不能只复述作者结论。
- 独立审查优先从已确认需求、源码和记录的基线出发，检查缺失分支、无效断言、过严断言、被遮蔽的副作用及未实际运行的用例；必要时加一个独立反例。维护者负责裁决模糊契约。执行者不能以自己的正确性判断替代既有验收条件。
- 结果以规范 runner 的退出状态、实际测试/跳过记录以及可复查的输出、状态或制品为证据。Agent 的文本报告、覆盖率变化或模型评分不能替代这些证据。此分工是 OMP 的约定，不是外部强制标准。

### T6：验证范围必须可追溯

- 在[贡献指南](../CONTRIBUTING.md#checks)选择受影响的本地检查，提交 PR 前依该指南跑完整验证。仅跑某个测试文件不等于包检查；受影响 PR CI、完整本地/主线 CI、真实制品验证和现场验收，各自证明的范围不同。
- 记录代码基线、命令（含工作目录和过滤参数）、环境（Node、pnpm、实际 Pi SDK 版本及相关变量）、退出状态和失败/跳过。如果缺 pnpm store、未获真实端点授权、没有 GUI 或没有运行某层检查，明确写出未验证的边界；不把缺前置条件等同于代码缺陷或通过。普通验证不授权发版、真实通知、付费调用或改本机设置。

## 审查与批量修复交接

审查者先固定提交和工作树状态，按工作区及共享套件划边界。优先看权限/数据边界、流重试或重放、子代理取消与隔离、通知副作用以及制品和发布验证。对每个发现引用 `T1`–`T6` 中适用条款并给出文件/行号；同一根因合并，区分**已证实违规**、**待验证**及**不适用**，不要把未覆盖到的区域记为通过。审查默认只交发现和证据，不混入修复。

每个可派发条目至少包括：

```text
编号 / 条款 / 状态：
基线（提交、工作树状态） / 归属（包或共享套件） / 文件:行：
契约与风险（会漏掉什么、可能破坏什么）：
证据（命令、环境、实际结果；未跑写明原因）：
最小修复范围 / 验收（错误情形和现有正确情形各如何验证）：
```

分批优先处理能放过错误、影响权限或发布边界的缺口，再处理不稳定、重复或难维护的测试。
修复执行者只接收已确认的范围和验收，尽量按不重叠的文件分工；共享 fixture/契约指定同一所有者。合并批次前，由独立审查者比对规则及原始发现，重新跑合并后的相关检查，不把各执行者的零散绿灯当作组合验证。
